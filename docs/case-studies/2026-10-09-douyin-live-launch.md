# 几何战争：从提审反馈到抖音直播玩法上线

2026 年 10 月 9 日，项目负责人反馈「几何战争」已审核成功并上线。本文记录本项目在此之前处理的礼物链路、画面适配和交付问题，供其他开发者参考。

上线结论来自负责人当日反馈；本文没有公开平台后台截图、审核原始事件日志或私有规范材料。源码与本地验证能解释修复做了什么，不能独立证明每个真实直播间场景，更不能保证采用相同实现的其他项目必然通过审核。平台要求应以各项目提交时能够取得的最新规则为准。

本文主要复盘 2026 年 10 月 8 日的两轮工作：[1.1.16 提审修复记录](../verification/2026-10-08-review-fixes.md)和[1.1.17 玩法、布局及交付记录](../verification/2026-10-08-gift-rules-1.1.17.md)。这些历史记录写下「平台待验收」时，本地验证确实尚不能证明上线；10 月 9 日的负责人反馈是后续信息，不应倒写成当时已经完成平台验收。

## 1. 先区分反馈现象与已经证明的原因

负责人确认失败包为 1.1.15，反馈集中在召集说明缺失、礼物没有可见效果，以及外显文案需要调整。礼物截图涉及能力药丸的批量赠送和能量电池，因而排查不能只验证本地按钮能否触发一个动画。

已经确认的代码缺陷是：旧 provider 在 `IsTestData=true` 且 `AllowPlatformTestGifts=false` 时提前丢弃礼物。10 月 8 日修复记录核对的当时平台说明表明，这类测试数据也包含版本审核互动测试。将「不计入正式统计」实现成「不执行互动」，会让审核测试事件到不了玩法层。

这里仍有一个必要的边界：没有取得那次提审的原始事件日志，因此不能断言所有真实付费礼物都走过这个分支。准确的结论是发现并修复了一个与审核现象吻合的入口缺陷，而不是凭截图猜出了每条事件的来历。

可复用的排查方式，是分别确认 SDK 是否收到事件、provider 是否成功解析、中立事件层是否投递、玩法是否改变状态、画面是否给出反馈，以及履约消息是否提交。只有逐段定位，才能区分礼物映射错误、错误会话、重复事件、玩法条件不满足和纯显示问题。

## 2. 让平台礼物与回归测试走同一条业务链路

当前实现的主要路径如下；本地开发协议只是测试入口，不等同于平台 SDK 协议。

| 环节 | 职责与源码 |
| --- | --- |
| SDK 宿主 | [DouyinSdkHost.cs](../../Tools/DouyinSdkHost/Runtime/DouyinSdkHost.cs)投影 SDK 礼物字段，保留数量、原消息标识与测试标记；数量以十进制字符串跨进程传输，避免经过浮点数丢失大整数精度。 |
| 平台适配 | [DouyinLiveProvider.cpp](../../Plugins/DouyinLiveProvider/Source/DouyinLiveProvider/Private/DouyinLiveProvider.cpp)中的 `FDouyinGiftDecoder` 负责解析与校验；生产投递和契约测试复用这个解码器。 |
| 中立事件层 | [LiveInteractionSubsystem.cpp](../../Plugins/LiveInteraction/Source/LiveInteraction/Private/LiveInteractionSubsystem.cpp)处理会话、事件投递与重放边界，玩法侧接收 `FLiveGift`。 |
| 玩法与反馈 | [ArenaGifts.cpp](../../Source/GeometricWarfare/ArenaGifts.cpp)判断礼物、数量、身份和当前阶段，调用模拟逻辑并生成带实际结果的通知。 |
| 履约 | [ArenaLiveInteraction.cpp](../../Source/GeometricWarfare/ArenaLiveInteraction.cpp)排队原消息 ID / type，在渲染阶段后提交 ACK，再由宿主调用 SDK 的 `ReportAck`。本地模拟不伪造平台履约。 |

测试数据也必须通过合法礼物、正数量、有效接收对象和当前会话等校验。测试标记不能把未知礼物变成奖励；同样，无法识别的加密礼物 ID 也不能靠猜测映射到某个已知礼物。礼物名称与 ID 的映射应有平台或项目配置依据。

数量采用新增数量语义；不能把连击累计值反复当成新增赠送。正式链路保留 `int64` 数量，不沿用本地演示入口的数量上限。重复 SDK 事件不得再次增加生命、重复发放权益或刷新弹药。

回归应覆盖真实解码器到委托、效果、权益与 ACK 的连接，而不只直接调用一个 GM 方法。可参考[礼物集成测试](../../Source/GeometricWarfare/ArenaGiftTests.cpp)和[平台事件集成测试](../../Source/GeometricWarfare/ArenaLiveInteractionTests.cpp)。客户端 ACK 提交成功与平台实际认可履约仍是不同的证据层次。

## 3. 执行测试效果，同时隔离正式权益和统计

修复没有删除测试标记，而是将其保留为 `bIsTestData`，一路传到玩法、通知和结算判断中。

- 正式武器礼物进入正式权益保存流程；平台测试武器只进入当前会话的临时权益集合，不写成永久付费权益，也不把临时装备写入正式的左手选择存档。
- 通知合并键包含测试标记。即使昵称、礼物和文案相同，测试与正式通知也不能混合；大量事件合并成多人播报时，测试武器仍只能描述为本会话权益。
- 会话切换同时重置战局、观众对象和临时权益，避免只清空临时映射，却把武器留在仍然存活的角色对象里。实现见 [HandleSessionChanged](../../Source/GeometricWarfare/ArenaGameMode.cpp) 与 [ArenaLiveRounds.cpp](../../Source/GeometricWarfare/ArenaLiveRounds.cpp)。

统计隔离采用了保守的会话范围：收到平台测试礼物后，该会话后续生成的结算不提交正式个人战绩、房间榜和世界榜，但仍关闭平台对局生命周期。原因是测试强化可能击败其他观众、改变队伍结果，并影响后续回合；只剔除测试礼物接收者，仍可能留下被测试效果改变的正式分数。

这个选择也有代价：同一会话里未直接接收测试礼物的真实参与数据，也会退出正式统计。它适合本项目当前的状态模型，不是所有玩法都必须照搬的最小隔离方案。如果需要更细的边界，应先证明哪些状态不会跨观众、跨回合传播。

结算快照一旦生成，不应被后来到达的测试礼物改写。当前结算与重试过程见 [ArenaLiveRounds.cpp](../../Source/GeometricWarfare/ArenaLiveRounds.cpp) 和 [ArenaLiveRoundOutbox.cpp](../../Source/GeometricWarfare/ArenaLiveRoundOutbox.cpp)；历史快照与当前会话状态要分别处理。

## 4. 将礼物规则写成状态转换，再同步到常驻说明

短暂出现的播报不足以说明全部规则。画面中的五种礼物需要始终有名称、图标、实际效果与关键使用限制；未触发时也要明确解释原因，而不是显示一个看似成功的通用动画。

| 礼物 | 本项目的实际规则 |
| --- | --- |
| 仙女棒 | 已入场本人阵亡时首件复活；存活时或复活后的批量余件，每件增加 30 基础最大生命。加成死亡清零，结算期间无效。 |
| 能力药丸 | 红蓝基地已毁时首件重建，余件增加基地当前 / 最大生命各 1000；基地尚存时每件均强化。冲刺和结算期间无效。 |
| 魔法镜 | 正式权益解锁左手狙击枪；重复赠送不补弹。 |
| 甜甜圈 | 正式权益解锁左手机枪；重复赠送不补弹。 |
| 能量电池 | 正式权益解锁左手火箭筒；重复赠送不补弹。 |

武器礼物可先保存未入场观众的正式权益，入场后装备；结算期间收到则下一局可用。上述永久权益描述不适用于平台测试礼物。仙女棒和药丸不会替未入场观众自动创建角色。

仙女棒尤其需要独立保存基础加成，不能只做一次 `maxHp += 30`。否则换形、进化结束或成为英雄时，重新计算上限就会覆盖这次赠送。以本次生命中的累计加成为 `B`，当前公式是：

| 状态 | 最大生命 |
| --- | --- |
| 普通观众 | 形状基础生命 + B |
| 非英雄进化中 | (形状基础生命 + B) × 2 |
| 英雄，含进化状态 | 2100 + B |

存活时收到 `N` 件，`B += 30 × N`；当前生命增加相同的上限增量，保持受伤缺口，不额外补充护甲。阵亡时先消耗一件复活，余下 `N - 1` 件再强化，不储存未来复活次数。换形保留加成；死亡立即清零；换局清零；进化到期只去掉进化倍率。英雄的固定基础上限与进化不重复相乘，沿用此前平衡规则。

实现集中在 [ArenaMatch.h](../../Source/GeometricWarfare/Simulation/ArenaMatch.h) 的 `applyFairyWand`、`maxHpFor` 与死亡流程，以及 [ArenaEvolution.inl](../../Source/GeometricWarfare/Simulation/ArenaEvolution.inl)。[ArenaRoundUpgradeTests.cpp](../../Tests/ArenaRoundUpgradeTests.cpp)覆盖计数、受伤缺口、换形、进化、英雄、死亡、复活、换局和治疗反馈。

10 月 8 日最终实图还核对了三个具体结果：受伤圆形收到两件后为 `260/360`；进化中对应为 `520/720`；阵亡收到三件后为 `360/360`。角色旁数值、选中详情与通知数量必须一致。这比只检查「有一个礼物动画」更容易发现生命周期错误。

常驻说明在 [DrawGiftRules](../../Source/GeometricWarfare/ArenaHUD.cpp) 中按可用空间测量。缩小窗口后，不能把条件藏进省略号、轮播或滚动区域；批量规则、死亡清零、入场和阶段限制使用公共脚注完整展示。

## 5. 比例适配要同时处理世界视口、输入和通知队列

第一轮手机画面虽然改变了外层比例，战场仍按正方形短边布局；常驻规则与榜单挤占空间后，战场很小，多条加入通知又覆盖了剩余区域。这个问题不能只靠统一缩放整个 HUD 解决。

最终做法是让战场填满剩余矩形，同时保持世界在两个方向使用同一个缩放比例。世界物理尺寸仍为 `2000×2000`；长轴决定可见世界跨度，短轴裁剪视野，不把圆形拉成椭圆。拖动、鼠标缩放锚点、点击反投影、跟随边界和小地图都必须使用同一套矩形计算。相关代码在 [ArenaView.h](../../Source/GeometricWarfare/Simulation/ArenaView.h)、[ArenaHUD.cpp](../../Source/GeometricWarfare/ArenaHUD.cpp) 与 [矩形输入测试](../../Source/GeometricWarfare/ArenaHUDInputTests.cpp)。最小缩放下也可能需要拖动或小地图查看短轴以外的区域。

通知适配还涉及业务计时。旧模型允许礼物、奖励、加入分别占多个活跃槽。如果绘制时只保留第一条，其他条目仍会独立到期，形成漏播。

当前紧凑布局将每类活跃槽调整为一条：礼物与奖励在顶部并排，加入消息贴底并避让小地图。减少槽位时，被移出的通知按顺序回到队列前方并获得完整展示时长；保留的活跃通知不重置年龄，避免持续连击长期占位。身份、数量、实际结果和测试来源继续参与合并判断。实现与测试分别在 [ArenaNotifications.cpp](../../Source/GeometricWarfare/ArenaNotifications.cpp)、[ArenaNotificationTests.cpp](../../Source/GeometricWarfare/ArenaNotificationTests.cpp)。

卡片宽度、字号与布局使用实际可用空间，关键礼物名、数量和效果完整换行；昵称可以截短。截图要包含三类通知同时出现的压力场景，而不仅是没有播报的整洁主界面。

## 6. 比分条不能以牺牲具体数字和昵称为代价

顶部红蓝总分以 `max(1, 红方分数, 蓝方分数)` 为共同上限；排行榜以 `max(1, 本局榜首分数)` 为共同上限，包括翻页之后的条目。进度条表达当前相对分数，没有增加新的积分胜利门槛。

条内显示完整十进制整数并居中，不增加分母，也不转换成 K/M 或省略号。零分仍有空底和数字 `0`。共享 [ScoreBar](../../Source/GeometricWarfare/ArenaHUD.cpp)使用字体实际测量结果处理尺寸与居中。

实图发现，强行把积分条塞进原来很窄的右栏会把普通昵称压成一个字加省略号。最终右侧榜单采用双行：第一行保留昵称、装备和状态，第二行放满宽积分条；手机下方榜单利用横向空间保留紧凑单行。行高改变后，分页数量、点击区域和跟随选择也一起调整。实现见 [DrawAdaptiveRanks](../../Source/GeometricWarfare/ArenaHUDAdaptive.cpp) 与 [DrawDesktopHUD](../../Source/GeometricWarfare/ArenaHUD.cpp)。

常规数字、全零和 19 位整数都需要独立截图。数学比例正确，不代表数字没有被字体缩放、布局遮挡或裁切。

## 7. 文案修复需要与功能入口一起验证

本轮根据项目收到的反馈调整了外显用词，例如「玩法设置」「能量条」「观众」「连续击败」「强化」。这些是本项目的文案处理经验，不应被当成一份对所有项目永久有效的禁词表；内部代码中的 `hp`、`heroBuff` 等技术名称也不等于观众看到的文案。

检查范围应包括主界面、设置、礼物条件、实际播报、多人汇总、结算、调试预览和交付说明。只替换一张贴纸，容易遗漏动态字符串或不同阶段的反馈。

召集指引被做成不依赖外部图片参数的常驻内容：「一键摇人 · 召集好友」及「小摇杆 → 召集 → 发起召集」。真实召集关系进入对应事件处理，普通分享或看播不冒充召集，也不凭空承诺奖励。代码入口见 [ArenaLiveInteraction.cpp](../../Source/GeometricWarfare/ArenaLiveInteraction.cpp) 和 [DrawRecruitSticker](../../Source/GeometricWarfare/ArenaHUD.cpp)。
