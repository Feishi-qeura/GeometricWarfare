# 几何战争玩法设计草案

更新日期：2026年10月2日。

本文记录 UE 5.8 项目 GeometricWarfare 已确认的直播互动玩法，以及仍需确定的边界。目标是以观众头像几何体、自动物理运动和独立枪械构成五分钟红蓝夺分对局。首个开发里程碑仍是抖音接入插件、角色生成和物理场景；本文同时约束后续完整玩法，不能把尚未实现的功能视为现有工程能力。

标为“已确认”的内容来自用户原始要求及逐项选择；标为“建议”或“待确定”的内容尚未成为正式规则。当前文档是设计稿，不是已批准的实施计划。

## 已确认的整体规则

- 游戏为 2D，使用 UE 5.8，场地为正方形。
- 观众发送“加入”生成专属角色。未来确认官方入场事件能力后，可以增加自动加入入口。
- 角色由上方昵称、中间几何体与头像、下方血条组成。
- 初次生成随机选择圆形、正方形、长方形、三角形，默认为灰色中立阵营。
- 角色生成后向随机方向移动；角色之间及角色与边界产生物理反弹。
- 红蓝角色参与积分、排行榜和胜负；灰色观众不持有积分、不拾取积分球、不进入排行榜。
- 每局固定 300 秒，时间到后阵营总分高者获胜。一方暂时全员死亡不会提前结束。
- 最后 60 秒进入冲刺阶段，红蓝基地同时摧毁且不能重建，个人仍可以通过指定礼物复活。
- 枪械是独立物品，所有几何体初始装备手枪。
- 抖音接入部分独立封装为 UE 插件。

## 加入与形状指令

用户要求使用数字选择阵营和形状，按当前阵营解释数字，避免含义冲突。

| 角色状态 | 输入 | 效果 |
|---|---|---|
| 未生成角色 | 加入 | 生成随机形状的灰色角色 |
| 灰色角色 | 1 | 加入红方 |
| 灰色角色 | 2 | 加入蓝方 |
| 灰色角色 | 3 或 4 | 不更换形状，提示先选择阵营 |
| 红蓝角色 | 1 | 圆形 |
| 红蓝角色 | 2 | 正方形 |
| 红蓝角色 | 3 | 长方形 |
| 红蓝角色 | 4 | 三角形 |

建议每条指令只执行一次状态转换。例如灰色角色第一次发送 1 只加入红方，再次发送 1 才切换圆形。重复“加入”应定位或高亮已有角色，不重复创建，也不绕过死亡状态。

建议本局加入红蓝后锁定阵营；换形保留武器、积分及生命比例，不刷新弹匣和攻击计时，并设置冷却。具体换形冷却及是否允许死亡期间换形待确定。

## 场内对象

| 对象 | 身份与行为 | 积分关系 |
|---|---|---|
| 红蓝观众角色 | 有头像与昵称，自动移动和战斗，有所属基地 | 收集积分并参与排名 |
| 灰色观众角色 | 有头像与昵称，可攻击也可被攻击，无基地 | 不持分、不拾取积分球、不上榜 |
| 中立 NPC 几何体 | 场内不移动的资源目标，与灰色观众分开管理 | 被击败提供高分 |
| 原生资源球 | 场地自然生成的可收集小球 | 提供基础积分，适用正方形倍数 |
| 死亡掉落积分球 | 灰色击败红蓝后生成 | 按原值回收，不适用正方形倍数 |
| 红蓝基地 | 可被攻击摧毁的阵营设施 | 控制自动复活资格 |

建议基地左右对称分布，中部布置更多高价值 NPC。灰色观众使用灰色阵营轮廓，NPC 使用不同纹理且没有观众头像，避免混淆。

## 对局时间和基地

| 时段或条件 | 红蓝自动复活 | 基地重建 | 灰色复活 |
|---|---|---|---|
| 前 240 秒，己方基地存在 | 死亡后 2 秒 | 基地已存在时的礼物处理待确定 | 死亡后 5 秒 |
| 前 240 秒，己方基地被摧毁 | 死亡后不能自动复活 | 对应阵营送指定礼物可重建 | 死亡后 5 秒 |
| 第 240 秒起，最后 60 秒 | 停止自动复活，允许个人礼物复活 | 双方基地强制摧毁，禁止重建 | 死亡后 5 秒 |
| 第 300 秒 | 对局结束，停止对本局继续生效的战斗和积分操作 | 对局结束 | 对局结束 |

基地被摧毁不等于阵营立即失败；当时仍存活的角色继续行动。每局坚持运行满 300 秒，以保留礼物复活后的追分机会。

建议在基地被摧毁或冲刺开始时，取消尚未完成的红蓝自动复活倒计时，并在实际复活前重新检查资格。建议前四分钟基地重建后，为该阵营等待复活的角色重新开始 2 秒倒计时。这两个边界尚待确认。

基地生命值、重建生命值、重建礼物及数量、个人复活礼物及数量、个人礼物复活等待时间均未指定。实现时应使用可配置规则，不应自行将某个礼物设为正式付费效果。

## 几何体属性与枪械

| 形状 | 最大生命 | 用户指定特性 |
|---|---:|---|
| 圆形 | 300 | 受到伤害减少 50%；换弹时间减少 50% |
| 正方形 | 250 | 获得双倍分数；对中立单位伤害增加 150% |
| 长方形 | 200 | 瞄准距离增加 50%；瞄准精度增加 50%；瞄准时间减少 50% |
| 三角形 | 300 | 伤害增加 50%；碰撞具有 15 点伤害 |

正方形双倍分数的适用范围已经单独确认：仅原生资源球和中立 NPC 奖励。角色之间的积分转移、死亡积分球回收都使用原值。

“对中立单位伤害增加 150%”表示基础伤害乘以 2.5。中立目标标签是否同时包括灰色观众，尚未确认。

枪械数据应独立于形状，包括基础伤害、射速、弹匣容量、换弹时间、子弹速度、瞄准距离、瞄准时间和散布。所有角色初始使用手枪；其他枪械的获取、替换和死亡后保留方式尚未指定。

建议瞄准精度使用独立属性再换算成散布角，避免直接对命中率增加百分比。具体换算公式待确定。

普通角色的身体碰撞只产生物理反应，三角形是碰撞伤害例外。建议同阵营不受友军伤害；三角形对同一目标设置碰撞伤害间隔，避免一次持续接触反复扣血。15 点是否还受到三角形伤害加成、碰撞触发间隔及伤害修正顺序均待确定。

## 积分来源与转移

| 事件 | 普通形状所得 | 正方形所得 |
|---|---:|---:|
| 拾取基础为 P 的原生资源球 | P | 2P |
| 击败基础奖励为 N 的中立 NPC | N | 2N |
| 击败当前持分为 S 的敌方红蓝角色 | 转移 S | 转移 S |
| 拾取价值为 D 的死亡积分球 | D | D |

红蓝之间击败按积分转移设计：被击败者积分归零，击败者获得其当前积分。例如红方甲 80 分，蓝方乙 120 分；甲击败乙后变为 200 分，乙归零。夺分本身不产生第二份积分。

灰色击败红蓝的处理已经确认：受害者当前积分归零，在死亡位置生成等值积分球，供红蓝拾取；灰色不获得隐藏积分，也不拾取这些球。

例如红方角色携带 100 分，被灰色击败后，掉落球总值为 100。任意红蓝形状完整拾取后获得 100 分，包括正方形。掉落球数量可以与表现分离，但总价值必须精确守恒。

原生资源球与死亡积分球必须记录不同的来源类型，不能仅凭外观识别。否则正方形可能错误地对死亡积分再次翻倍。

建议阵营总分等于该阵营全部参与者当前持有积分之和；每次积分转移或掉落都同时更新个人与阵营账目。掉落在场上尚未拾取的积分不属于任何阵营。

灰色击败 NPC 是否产生供红蓝拾取的奖励球、红蓝击败不持分灰色是否有额外固定奖励，以及环境导致死亡时的积分处理，均待确定。

## 排行与结算

已确认排行榜排除灰色，胜负只在红蓝之间比较。五分钟到时比较阵营总分，一方全灭不提前结算。

建议直播画面顶部展示红蓝总分、基地血量或摧毁状态、剩余时间；侧边展示本局个人积分榜。个人条目包含头像、昵称、阵营、当前积分及存活状态。死亡角色不应直接丢失身份记录，方便礼物复活和本局结算。

本局个人榜与小摇杆本局榜建议采用同一积分口径。长期累计榜是另外的产品范围，不与本局可转移积分混用。

阵营平分时的胜负处理、个人同分时的排序、结算展示时长及下一局保留哪些信息尚未确定，不能先写成已确认规则。

## 抖音接入设计与文档依据

官方存在 LiveOpenSDK，包含长连接指令直推、直播信息、履约 ACK、对局与阵营同步、直播间维度的对局榜单等能力。自建 HTTP 回调服务不是所有接入方式的必经步骤。[官方 SDK 概览](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/develop/unity-sdk/overview)

当前查阅的公开安装指南明确使用 Unity 2020 及以上 LTS、C# 和 BGDT 分发。UE 5.8 是否可以直接封装其原生接口，仍需取得实际 SDK 包并检查接口、依赖、授权范围和目标平台；不能将 Unity 包描述为已验证可用的 UE SDK。[官方 SDK 接入指南](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/develop/unity-sdk/unity-sdk-access)

项目内建议插件名为 DouyinLiveBridge，提供统一的加入、评论、礼物、阵营选择和连接状态事件，并承接对局、阵营、榜单及履约上报。游戏模块负责形状、武器、伤害、基地、复活和积分。连接层可以替换，而不改变玩法规则。

加入入口继续采用已确认的评论“加入”。目前并未验证对所有观众的直播间入场通知；增加自动加入需要单独确认能力。官方快捷选队提供额外的选队按钮入口，点选结果需要独立处理，不能假设还会收到相同的评论。[快捷选队](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/advanced-interaction/quick-select)

礼物能力支持按阵营配置效果；项目中的阵营标识应与相关能力配置保持一致。基地重建与个人复活分别作为玩法效果处理，同一礼物消息重复到达不得重复履约。[礼物互动能力](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/hudongshuju/liwushuju)

官方用户战绩与排行榜能力可在小摇杆展示单局榜、总榜及历史战绩。应根据所选 SDK 或 OpenAPI 覆盖范围确定接入方式；不能把 SDK 的直播间榜单能力当作跨直播间世界榜。[用户战绩与排行榜](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/advanced-interaction/user-rank)

以下能力暂不作为首个里程碑的前置条件：

- 玩法扩展组件：本质为与直播玩法关联的抖音小游戏。[扩展组件说明](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/advanced-interaction/gameplay-expansion)
- 透明画布：可组合主播和玩法画面，所查文档限定直播伴侣场景。[透明画布说明](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/pingtaijichu/transparent-bg-guide)

正式提案还应描述指令、礼物效果、排行规则与完整流程。用户提供的 DOCX 是提案参考模板，模板中的礼物样例不自动转为本项目需求。[规则介绍模板](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/design/design/RulesTemplate)

## 建议的实现边界

首个里程碑保持原始范围：独立平台插件、本地模拟入口、唯一观众角色、头像昵称与血条、随机四种几何体、正方形地图和稳定的平面物理反弹。真实平台接入和模拟模式必须明确区分，模拟通过不能代替真实接入验收。

后续按依赖顺序增加：阵营与换形、独立手枪与属性、资源球和 NPC、积分与榜单、基地与复活、五分钟回合、礼物效果与平台结算。具体任务和验证命令属于后续实施计划。

建议内部模块边界如下：

| 模块 | 责任 |
|---|---|
| 平台插件 | 平台事件、连接、消息去重和上报，不决定战斗效果 |
| 观众注册表 | 观众唯一身份、角色引用、阵营与死亡状态 |
| 回合管理 | 300 秒计时、240 秒阶段切换、终局状态 |
| 物理与角色 | 二维约束运动、碰撞和形状外观 |
| 武器与伤害 | 装备、瞄准、射击、伤害与击败归属 |
| 基地与复活 | 基地状态和复活资格，在执行时重新校验 |
| 积分管理 | 积分来源、转移、掉落和阵营汇总 |
| HUD 与榜单 | 用户信息、规则提示、基地状态、榜单和结算 |

## 后续验证重点

- 同一观众重复加入、重复评论或重放礼物不会创建重复角色、重复积分或重复复活。
- 四种几何体不会穿墙、长时间重叠或无限加速；头像加载失败不阻塞角色运动。
- 一次死亡只结算一次积分；原生奖励适用正方形倍数，转移和死亡掉落不适用。
- 灰色击败后的掉落总值与被扣除积分一致；灰色不持分且不进入榜单。
- 基地摧毁与角色复活同时发生时，不会绕过最新复活资格。
- 第 240 秒准确进入冲刺；第 300 秒冻结本局结算，一方全灭不会提前结束。
- 礼物延迟到达、目标已复活、基地已存在或已经进入禁止重建阶段时，效果与履约处理必须有明确规则，不能悄悄消耗却无反馈。
- 平台测试数据与正式榜单隔离；真实接入需使用官方测试环境完成联调。
